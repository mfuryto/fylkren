# Enterprise AI assistance

## Purpose and supported first slice

Fylkren provides optional, bounded AI assistance as an Enterprise capability. It is disabled by default and the rest of Fylkren remains fully operational without a model or network connection. Platform Manager configures one OpenAI-compatible chat-completions endpoint, model and optional protected API key, selects the Sites allowed to use it, and enables any of four functions:

- summary and quality checks;
- separate bounded planning, risk/mitigation and decision-basis drafts;
- analysis of learning points;
- questions about one work item.

Summary, quality review and questions are available from an open task. Planning assistance is opened from the current planning step, reads every step in that run's snapshotted template, and returns a separate proposal for every template step. **Use this draft** distributes the proposals to their corresponding rich-text editors; it cannot place a combined plan in the open step. The server requires the template headings and checklist structure to remain present and rejects missing, duplicate or unknown step numbers. The existing editor/autosave endpoint then applies the same authorization, audit and activity behavior as manual text.

Risk assistance is located in the risk workspace and returns at most five separately reviewable proposals with title, cause, consequence, mitigation and an optional supported deadline. The authorized existing risk register, including closed risks and current mitigations, is supplied as bounded context so the provider is instructed not to repeat registered matters. Suggestions are handled one at a time through a visible four-step flow: select proposal, assess probability and impact in the map, review mitigation, and register. A handled suggestion is removed only after successful registration. The provider is not allowed to set probability or impact. Decision assistance is located in the decision workspace and returns at most three separate suggestions with title, recommendation or unresolved choice, and rationale. Applying one opens the ordinary decision editor, where the user explicitly saves a draft or records the decision. Draft editing/deletion and recorded-decision revision/withdrawal use the existing numbered revision model; no AI action changes decision state. Learning analysis is opened from a learning point on the Learning page and groups, deduplicates and prioritizes the authorized learning points for that work item without treating or closing them. AI never changes status, approves work, closes risk, publishes a plan, sends a request or alters access.

Every operational AI entry point uses the same labelled assistance button and sparkle icon. Its text describes the help offered in the current context: **Analyse task**, **Suggest plan content**, **Identify risks and actions**, **Suggest decision basis** or **Analyse learning points**. The distinct treatment is intentionally more visible than a generic secondary action, includes a shared working state, and remains compact enough for task cards and workspace headings. This makes AI an available helper while keeping every consequential domain action on its ordinary non-AI control.

## Architecture and data flow

`POST /api/ai/sites/{siteId}/work-items/{itemId}/assist` is the sole operational entry point. The API verifies the Enterprise `ai-assistance` entitlement, global enablement, explicit Site selection, browser antiforgery token, rate limit and the caller's ordinary work visibility before assembling context. Learning content is filtered again through the existing exact-level learning policy. The web client supplies its active supported locale, and the API repeats the required output language in both the trusted system instruction and after the untrusted context; older clients fall back to the installation language. The model never receives database access, a Fylkren credential, a tool interface or authority to choose another endpoint.

A planning request additionally identifies the active workflow run and current step. The server requires that the caller currently owns the in-progress run and still has planning authority at that work level. A stale or different step is rejected. The context contains the workflow name and every ordered step document. Those documents are the run-specific copies created when planning began, so later edits to the template library cannot silently change an active plan's AI basis. Template headings, checklists, placeholders and order are authoritative; unsupported fields remain visibly missing rather than being invented. The response is a server-validated step array and uses the editor's bounded Markdown subset, which the rich-text editor renders rather than displaying as formatting characters.

Risk and decision generation uses strict server-validated JSON contracts. Unknown properties, excessive item counts, missing/oversized text, invalid deadlines and provider-supplied risk scores are rejected before anything is shown as a usable draft. The browser receives typed draft fields rather than raw provider JSON. Learning retains the exact-level `LearningPolicy` filter and sends only learning points for the selected work item that the caller may read.

The configured endpoint normally must be an absolute HTTPS chat-completions address. An installation may explicitly permit an HTTP origin for an AI provider only when the exact origin is listed in `FYLKREN_OUTBOUND_PRIVATE_ORIGINS` and every resolved address is private or loopback. This narrow exception does not apply to webhooks, federation or identity providers. Redirects and oversized responses are rejected. Interactive assistance uses provider streaming and relays bounded text deltas as newline-delimited JSON so the user sees the answer while it is generated; the stored connection test remains non-streaming. If a compatible provider rejects streaming with HTTP 400, Fylkren performs one non-streaming compatibility fallback and returns that result through the same browser response format. During this fallback the API emits a content-free heartbeat every 15 seconds so an idle-read proxy does not discard an otherwise healthy long-running request. This fallback is limited to an explicit stream-mode rejection and is not used for rate limits or server errors. Neither path contains tools, both permit at most 1,400 output tokens and share one 300-second request deadline. The web gateway disables buffering on AI routes and retains its 330-second boundary. Fylkren appends the Qwen-compatible `/no_think` switch to the user message so the bounded completion budget produces visible answer text instead of provider reasoning. Providers that do not implement the switch receive it as an ordinary instruction to return only the answer. Provider `429` responses are returned without an automatic duplicate request and preserve a bounded numeric `Retry-After` value when supplied. The existing outbound destination policy blocks prohibited addresses; a private/local model endpoint additionally requires an exact deployment-owned origin in `FYLKREN_OUTBOUND_PRIVATE_ORIGINS`.

The provider key is protected with the installation's ASP.NET Data Protection key ring, is never returned to the browser, and participates in the governed protected-value re-protection process. Configuration changes, connection tests and assistance requests are recorded in the existing security audit. Prompt and response bodies are not written to audit or activity history. No domain activity is created because generating an uncommitted suggestion is not a domain event.

Every provider attempt forwards the API request's server-generated correlation ID as `X-Request-ID`. Fylkren logs only provider status, request start time, elapsed milliseconds and that correlation ID; prompts, responses, endpoint URLs and credentials are excluded. The same ID is returned in `X-Fylkren-Correlation-ID` and in streamed start/error events so an operator can match the browser failure with the API, reverse-proxy and model-host records. A stream-mode `400` and its non-stream fallback share the ID and represent one user operation. The fallback pair is not itself a provider failure; the terminal status determines the outcome.

## Trust and security boundaries

Work text is untrusted model input. The server system instruction tells the model to treat it as data, use only supplied facts, identify unsupported assumptions and never claim a Fylkren change. There is no model-controlled tool call, URL retrieval or permission choice. Requests and responses are bounded, and each response states the source work item's update time so users can detect stale output.

Selecting an external provider is a customer data-processing decision. The customer must assess the provider, contract, processing region, retention/training policy and the information classifications permitted to leave the installation. Fylkren's Site selection is a technical disclosure boundary; it does not replace that assessment. For restricted or air-gapped use, configure a locally operated compatible endpoint.

AI output is advisory. It may be incomplete or wrong. A human remains responsible for every decision, risk score, measure, plan, report and lifecycle action. Fylkren must not use this capability for identity decisions, authorization, security classification, personnel scoring, final approval, deletion or autonomous cross-Site/federated routing.

## Imported primary-document sources

When a task is created on an AI-enabled Site, the registering user may import its primary document. **Use the imported document as an AI source** is selected by default and may be cleared before registration. Selection of the file is the user's explicit source-access action; the import endpoint then reapplies authorization for the task creator, current level manager or current user who has claimed its active planning run. The separate reference URL remains available as the link to the original document and is captured with each imported version, but Fylkren never fetches it automatically. This avoids turning an arbitrary URL, file share or model response into a retrieval instruction.

Fylkren, rather than the model, extracts the selected document. The first supported formats are PDF, DOCX and UTF-8 plain text. The upload is limited to 8 MiB, 250 PDF pages and 100,000 extracted characters. Extension and declared media type must agree. DOCX archive count and expansion are bounded, unsafe paths and macro content are rejected, and encrypted, damaged, empty or unsupported documents fail without a snapshot. General web browsing, model-selected retrieval and direct `file` or `smb` access from the AI provider remain outside this capability.

The original file is discarded after extraction and is never served by Fylkren. Extracted content is a version-bound source snapshot identified by task, sanitized name, canonical media type, SHA-256 digest, source link, version, importing person and import time. Its JSON structure preserves ordered paragraphs/headings for DOCX, paragraphs for text and page boundaries for PDF. AI receives only the newest version explicitly marked available to AI. Every response identifies the snapshot name, version and digest it used, while Fylkren presents the original link locally without sending that link to the provider. Prompt and extracted content remain excluded from ordinary logs and audit metadata; the audit records only that a snapshot was imported. A changed document requires a new snapshot, so historical content is not silently rewritten. Site portability exports include all snapshot versions as customer data.

The document context is assembled once for the selected task and reused by every task-bound AI function: task summary and questions, planning, risks and measures, decision basis and learning analysis. Each call still applies its ordinary task, Site and feature authorization. A document from one task or Site is never added to another task's context.

Planning generation derives its expected steps, names and content markers from the active workflow template. It therefore supports different templates and step counts instead of assuming the standard plan. The provider is asked for simple tagged step blocks, which avoids fragile JSON escaping in long Markdown content. The response reader retains JSON compatibility and accepts harmless variations commonly produced by local models, including numeric strings, step names, ordered arrays, keyed step objects, extra descriptive fields and fenced JSON. It still requires every template step exactly once and verifies that each step retains its own headings and checklist markers before presenting editable drafts. Missing, duplicate or structurally misplaced steps are rejected. A dynamic per-step word budget keeps multi-step output within the provider token boundary.

The structured text and block JSON are an internal AI context, not an end-user document view. The task interface and primary-document read endpoint expose only the original-document link and import provenance such as name, version, type, digest and timestamp. They never return extracted text or structured content. Authorized users continue to read the original document in its source system. The structured snapshot is included only in the separately authorized Site portability export so the customer can retrieve its own retained data during an exit or preservation process.

The task and active planning interfaces show whether a primary-document snapshot exists and its current version. The details show its filename and whether that version is available to AI. An authorized user can select a new file in the same view; this creates the next retained version and makes re-import explicit instead of silently replacing provenance.

Direct retrieval through a configured internal connector remains a later extension. It must enforce the source system's user authorization, classification/disclosure policy, exact outbound destination, redirect and timeout controls before it can make a linked document eligible for import. The upload flow does not weaken that future connector boundary.

## Administration

Open **Platform Manager → AI**. Enter the full provider endpoint and model name, add the provider key when required, choose the allowed functions and Sites, then save and test the stored connection. The main switch immediately controls whether operational AI actions are available. Removing or losing the Enterprise entitlement blocks AI calls without deleting the stored setup.

For a private model, add its exact origin (scheme, host and port, without a path) to `FYLKREN_OUTBOUND_PRIVATE_ORIGINS` in the deployment environment and restart the API after changing that deployment-owned outbound boundary. The full chat-completions path remains stored through Platform Manager. HTTPS remains recommended. HTTP is an explicit closed-network exception: the Bearer key and task content are then readable to anyone able to observe that network segment, so the customer must accept and document that risk and restrict the destination port to the Fylkren host.

### Local Llama example

Local Llama models are supported through a server that implements the OpenAI chat-completions contract. Ollama and vLLM both provide this interface. Fylkren does not install or operate the model runtime itself. Prefer customer-controlled HTTPS. On an isolated and access-controlled network, the operator may instead approve the exact private HTTP origin:

```dotenv
FYLKREN_OUTBOUND_PRIVATE_ORIGINS=http://192.168.1.30:8443
```

Then configure Platform Manager with an endpoint such as `http://192.168.1.30:8443/v1/chat/completions`, the exact model name exposed by the runtime and the provider key when required. The listener must remain limited to the Fylkren source address and the dedicated route. Do not expose the model runtime's loopback port directly.
