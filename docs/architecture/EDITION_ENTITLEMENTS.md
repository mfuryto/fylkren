# Community and Enterprise entitlements for 1.0

## One product and one data model

Community and Enterprise use the same source tree, the same API and web image artifacts, database schema, migrations, APIs and upgrade path. The existing Compose stack has separate API and web containers, but there are no edition-specific builds or images. An edition is the **current effective entitlement state**, not an installation mode or a second product. No license or Internet connection is needed to install, run or upgrade Community. A valid signed offline license activates selected Enterprise capabilities immediately through Platform Manager's **License** page; no image replacement, reinstall or data migration occurs.

This decision must be in place before the final Fylkren 1.0 functional, integration and security acceptance run. The acceptance run must exercise both states and transitions in the exact artifact intended for release. Enterprise feature IDs are centralized in `apps/api/Licensing/FeatureCatalog.cs`; the Community active-site quota is centralized in `apps/api/Licensing/SiteCapacityPolicy.cs`. Changing either allocation before release changes a policy, not a domain model or a duplicate implementation.

| Capability | 1.0 allocation | Behavior without entitlement |
| --- | --- | --- |
| Up to three active sites (including child sites), unlimited internal units and personnel, local identity, MFA and passkeys/WebAuthn, task/plan/execution/report flow, templates, audit, notifications, and portable customer export | Community | Fully operational offline within the active-site limit. |
| Unlimited active sites | Enterprise | Creating or reactivating a fourth active site requires Enterprise. Existing sites remain usable after a downgrade. |
| Machine administration and report APIs (`machine-api`) | Enterprise | New clients/grants and machine API requests return `403`; existing client/grant metadata can be viewed and removed. Ordinary user access to sites and reports remains. |
| Webhook subscriptions and delivery (`webhooks`) | Enterprise | New subscriptions return `403`; delivery worker stops without deleting queued events, subscriptions or history. Existing subscriptions can be viewed and deactivated. |
| New AD/LDAP, OIDC and SAML identity linking, AD/LDAP personnel import and automatic AD/LDAP lifecycle synchronization (`external-identity`) | Enterprise | New links/search/import return `403`. Existing linked identities may still authenticate so license loss does not strand users or customer data; their automatic deprovisioning checks continue as a safety control. Existing links remain visible and can be removed. Local identity and MFA remain Community. |
| Trusted Fylkren-to-Fylkren instance federation (`instance-federation`) | Enterprise | Included for every valid Enterprise license, including licenses issued before this entitlement was introduced. Routing remains disabled until Platform Manager completes setup and activates it. |

Platform Manager always sees Enterprise-gated functions. Every unavailable capability uses the shared **Krever Enterpriselisens** notice and keeps its controls visible but disabled; unrelated Community controls on the same page remain usable. This presentation rule applies consistently to external identity, machine/report API, webhooks, federation and the site-capacity boundary. Server-side entitlement enforcement remains authoritative.

Authorization and entitlement are **both** required. The server checks entitlements on protected endpoints and background delivery; hiding a control in the web client is only a usability measure. An inactive, tampered, mismatched or expired license fails closed to Community. The API returns `403` with `code: enterprise_entitlement_required` and the stable feature ID for a protected action. Customer-owned data is never deleted or migrated on downgrade. The browser refreshes effective entitlements periodically; server enforcement is immediate and does not trust the browser's state.

## Offline license and trust

The runtime bundles the THUNOLD-OLSEN production P-256 ECDSA SubjectPublicKeyInfo **public** verification key. Its SHA-256 DER fingerprint is `9d52a2d724c72da913c9b87f2db2f8c8d4ac1f74cc1689ca14f6c0bf7b65e8fe`. The optional `FYLKREN_LICENSE_PUBLIC_KEY_SPKI` setting adds a second trusted public key for controlled transition or isolated tests; it does not replace the bundled key. The private signing key belongs only in the separate issuer environment and must never be stored in this repository, Docker image, customer database, application logs or Fylkren host. Community still needs no license file or Internet connection.

The portable JSON license envelope has `payload` (base64 of UTF-8 JSON bytes) and `signature` (base64, 64-byte IEEE-P1363 ECDSA P-256/SHA-256 signature over those exact bytes). Payload schema version 1 contains `licenseId`, `instanceId`, `customer`, `notBefore`, `expiresAt` and `entitlements`. The signed instance ID binds the license to the stable installation identity shown on the License page. The server validates signature, version, instance, allowed entitlement IDs and validity interval **before** replacing an installed license. A failed import preserves the prior license and data. The active envelope is stored in the common database; status is recalculated against current time on each protected action, so expiry does not require a restart or network call. Import and removal are audited without logging the raw license.

This signature boundary prevents a modified, fabricated, copied-from-another-instance or expired license file from enabling Enterprise in an unmodified official Fylkren build. It is not DRM against the owner of a self-hosted server. A party that changes and recompiles the source, replaces the bundled public key or patches server-side entitlement checks can create a different program that ignores licensing. Client-side hiding, obfuscation and self-checks cannot reliably prevent that when the party controls the host and source. Fylkren therefore relies on server-side checks for the official product, protected issuer-key custody, the source license and customer terms, plus signed release tags and published artifact digests to distinguish official builds from modified ones. Never describe the entitlement signature as proof that a customer-controlled executable is unmodified.

License generation, production private signing keys, customer/payment records and commercial backend logic belong exclusively in the separate private `thunold-olsen-licensing` repository. This public repository contains only verification keys/code and synthetic **pre-signed** fixtures for isolated automated tests; the fixtures' signing key is not a production trust anchor and is not stored here. Before real issuance, compare the bundled key fingerprint to the issuer portal, safeguard the production private key outside the distributable repository and images, and establish a documented rotation/recovery procedure. An added trusted public key requires an API restart; importing or removing a license does not. Retiring the bundled key would require a deliberate product update after previously signed licenses are accounted for. No online activation, telemetry, vendor callback, public CA or time service is required.

## Lifecycle and data safety

Community → Enterprise consists of importing a valid envelope as Platform Manager. Enterprise → Community occurs on explicit removal, signature/trust failure, or expiry. Existing work, reports, audit/history, external identity links, machine-client records, webhook subscriptions and queued deliveries remain in the same database. Community users can still view their normal customer-owned work and export their data. Sites created under Enterprise remain active and fully usable even if the active count exceeds three after downgrade; only creation or reactivation that would increase the count is blocked. Deactivation can free a Community slot, while historical records remain. Enterprise-only mutations and deliveries stop; restoring a valid entitlement resumes eligible operations after the ordinary authorization checks. A production recovery procedure must test backup/restore of both the database and matching installation identity so the signed license remains bound correctly.

Edition status and supported entitlements are exposed only to authenticated sessions in `/api/configuration`; detailed license metadata and offline import/removal are Platform Manager-only at `/api/platform/license`. The anonymous `/api/configuration/public` carries only what the sign-in page needs. Never include the private key or raw signed payload in either configuration response. Do not infer an edition from an environment toggle or frontend visibility.

## Software license is distinct

The repository's [PolyForm Perimeter 1.0.0 license](../../LICENSE) governs use of the current project-authored source; an Enterprise entitlement governs features enabled in an official running installation. Entitlement checks do not amend the software license. Before public distribution, obtain legal/commercial review of the license, customer agreement, feature-entitlement policy, copyright ownership and earlier MPL-2.0 history. Do not describe a runtime feature gate as a replacement for, or amendment to, the actual software-license terms.

## Release verification

Run the isolated edition E2E harness against a fresh database, synthetic pre-signed license fixtures and synthetic roles. It must cover no-license Community, signed Enterprise activation, tamper/wrong-instance/expired rejection, API and UI gating, Community → Enterprise, downgrade/removal, and continued data visibility. The site-quota scenarios must include creation of the first three sites, rejection of a fourth (including a child site), successful creation under Enterprise, downgrade with more than three still-active sites, reactivation after deactivation, and concurrent creation at the quota boundary. The [2026-09-27 automated API baseline](../testing/runs/2026-09-27-community-enterprise-api-regression.md) passed from fresh fixtures against the common artifacts, and the [Enterprise browser transition](../testing/runs/2026-09-27-enterprise-browser-transition.md) passed file-control activation, licensed-control, removal and retained-data checks. A live expiry/clock-transition test remains a separate release gate, because the public harness does not contain a signer. Then run the complete functional/integration/security suite with the same entitlement architecture. Do not represent instance-federation work delivery itself as tested by this edition suite.
