# Independent-instance federation

## Status and boundary

This document defines the implementation boundary and Enterprise contract. Federated work delivery is production-capable but **disabled by default**. An entitled Platform Manager completes bilateral setup and explicitly activates routing on each installation from **Federering**. Until then, peer administration, proof and catalog sync are available, while remote recipient selection, queue processing and work-message receipt remain closed. Activation is persisted and audited; it does not depend on `ASPNETCORE_ENVIRONMENT` or a server restart. Synthetic producer and answer-acceptance routes remain restricted to `FederationTest` and are never mapped in `Production`.

Federation must connect independent Fylkren installations, not API replicas of one installation. Each installation keeps its own database, authentication, site administration, work queues, audit and backup. Loss of a peer must not stop local operations. No shared database or database replication is permitted for federation. Federation is not high availability; clustered high availability is not on the product roadmap.

## Stable identities

A migration creates one `instance_identity` row per database with a random, durable UUID. Every API node sharing that database uses the same instance ID. Upgrade and restore preserve it. It is not a hostname, URL, certificate fingerprint, license ID or site name. Renaming an installation cannot change it.

The durable address of a site is `(instanceId, siteId)`. The durable address of a transferred domain object is `(originInstanceId, originSiteId, originResourceId)`. All three components are required when correlating work across installations; a local GUID alone is not a federation key. Locally generated site and work-item IDs and existing permalinks remain unchanged. Recipient search includes `instanceId`, and task creation, side-request and planning-request forms preserve it as `targetInstanceId`. A remote address is accepted only while routing is enabled and the exact peer, active catalog entry and Enterprise entitlement are active; otherwise it fails with `federated_recipient_not_routable` before it can enter a local-site path.

A restored disaster-recovery replacement of the **same** installation retains its identity and must not be connected simultaneously to a peer alongside the original. A cloned database intended to become an **independent** installation must receive a new instance identity through a controlled, audited re-key procedure before federation is configured. That procedure is not implemented yet; merely changing a URL or display name is unsafe. Portable site import is not instance cloning and requires explicit ID mapping where identities conflict.

## Site directory and selection

The federated site directory has a separate `federation_remote_sites` table. A remote site must never be inserted into the local `sites` table just to appear in a selector: that table denotes locally owned administration, personnel and task data. Catalog rows contain peer instance ID, site ID, display-name snapshot, active state and monotonically increasing catalog revision. A successful connection test and later explicit refreshes populate this table. An active snapshot becomes an eligible task destination only while routing, the Enterprise entitlement and its proved peer are active. Do not synchronize remote organization, users, workflows, task lists or reports. Display names are snapshots for user context, not stable keys.

There is no configured maximum peer count. Every installation stores and approves each peer relationship explicitly; a full mesh therefore grows quadratically with the number of installations. Only a two-installation pair is currently exercised end to end. The catalog contract allows at most 2,000 sites and a 1 MB response per peer sync, while the delivery page's newest-100 window is only a display bound. The maintained retention/load baseline verifies bounded cleanup and operative query indexes at 55,000 history rows per category, but does not establish a supported peer-count or production message-volume limit.

Federation addresses **top-level sites only**: a site with no parent organization unit (`ParentOrganizationUnitId == null`). Active top-level sites are automatically visible to every active, proven peer when it synchronizes the catalog. A child-site is not a top-level site and is never offered as a direct federated destination. A section, team or other internal unit is likewise never a federated destination. A request from any internal level or child-site crosses the instance boundary through its own top-level parent site; the remote top-level site then decides any internal distribution. Only top-level site names and the official top-level response cross the boundary, with coarse external status. This is a stricter destination rule than the current same-installation `RequestRecipientPolicy`, which can include sibling or other non-descendant child-sites. Do not silently change that local policy while implementing federation; any desired local-policy alignment needs its own review.

## Peer administration

Platform Manager can maintain peer records through `/api/platform/federation/peers`: `GET` lists records, `POST /discover` asks the remote HTTPS endpoint for a nonce-bound, signed identity proof, `POST` approves the discovered instance, `PUT /{instanceId}` changes its name/URL, and `DELETE /{instanceId}` deactivates it without erasing identity or audit history. Discovery returns the stable instance ID and SHA-256 SPKI fingerprint for independent comparison; approval repeats discovery server-to-server and atomically pins the proved P-256 key only if the instance ID and fingerprint still match. The other installation must perform its own discovery and approval, so trust remains bilateral and no node is central. No public key is copied through the browser. Planned rotation is automatic after a Platform Manager starts it: the node keeps its old key active while it sends every active, proved peer a recipient-bound statement signed by both old and new keys. Each peer verifies both proofs and stages the new pin. Only after every active peer returns a signed receipt does the node activate the new key; it then sends a new-key completion proof and retries until every peer has atomically replaced its pin. Work delivery remains queued during this short completion phase. An unavailable peer or a clock difference beyond five minutes leaves the old key active during staging and causes automatic retry; the protocol does not widen the time window. Replayed or overlapping messages are rejected and all state transitions are audited. This procedure does not recover a key whose old private material is already lost. Duplicate keys and the local installation's own key are rejected. Mutations require the `instance-federation` Enterprise entitlement, Platform Manager authorization and browser antiforgery validation; read access remains after license loss. Approval, update, deactivation and rotation actions are platform-audited. The API rejects the local instance ID, duplicate peer IDs, non-HTTPS URLs and URLs with credentials, paths, queries or fragments. A new peer cannot be approved while a rotation is in progress.

The local installation can generate its own dedicated P-256 federation signing key once via `POST /api/platform/federation/identity`; `GET` returns its installation ID, public SPKI key and SHA-256 DER fingerprint for a Platform Manager. Creation requires Enterprise entitlement, Platform Manager authorization and antiforgery, and is audited. The private PKCS#8 key is protected with the installation's existing ASP.NET Data Protection key ring before database storage and is never returned by the API. This key is independent of the Enterprise-license issuer key. Planned rotation is initiated by a Platform Manager and completed automatically between approved servers. Back up and restore the database **and** Data Protection key volume together; losing the key ring makes the protected private key unusable and requires a controlled recovery procedure. A discovered key alone never creates reciprocal trust or site authorization.

Each Platform Manager enters the other installation's HTTPS URL, retrieves its signed identity and compares the displayed fingerprint through an independent channel before approving it. Approval is repeated independently on the other node. Discovery proves possession of the advertised private key and records a local proof; `POST /api/platform/federation/peers/{instanceId}/probe` remains available as an explicit connection test. The probe endpoint accepts only HTTPS, an approved peer with a pinned P-256 key, a signed request addressed to its own instance, a five-minute timestamp window and a previously unseen nonce. It responds with a separately domain-separated signature over the same nonce. The initiator verifies the pinned response key, addresses, nonce and time before recording a successful proof and platform audit event. The receiver stores the nonce in PostgreSQL for cross-node replay prevention; expired nonce rows are cleaned after seven days. Peer HTTP calls use normal certificate verification, no redirects, no browser credentials and a ten-second timeout. An air-gapped deployment may use an internally trusted CA, but must distribute that CA through the host/container trust store; certificate validation is never disabled. Both clocks must agree within five minutes without requiring an Internet time service.

If the protected local private key can no longer be opened, the Platform Manager interface reports it as unusable and refuses planned rotation. `POST /api/platform/federation/identity/recover` will generate a replacement only while loading and validating the existing key fails; it cannot be used as a shortcut around planned old/new-key rotation. The replacement keeps the stable installation ID but does not update any peer automatically. At every peer, a Platform Manager must start a dedicated recovery discovery against the already configured HTTPS base URL, compare the newly proved fingerprint through an independent channel and explicitly approve that exact fingerprint. Approval replaces only that peer's pin, clears an incomplete rotation, suspends cached remote sites and is audited on both installations. A new connection test refreshes the catalog. A changed key discovered during an ordinary probe, catalog call or delivery remains unauthorized. Operators should first try a matched database and Data Protection key-ring restore; the recovery flow is for confirmed loss, not routine rotation or independent clone conversion.

A successful probe proves current possession of the pinned key and HTTPS reachability; it does **not** enable routing. Active local **top-level** site identities are included automatically in the signed catalog for every active, approved peer. There is no separate publication or site-pair decision in the GUI. Moving a site under a parent or deactivating it removes it from active discovery. Site names and hierarchy changes advance the signed catalog revision through the site's normal version.

`Test tilkobling` proves the peer and immediately synchronizes its site catalog. The receiving `POST /api/federation/v1/catalog` requires HTTPS, Enterprise entitlement, an active pinned peer, a signed v1 request addressed to its instance, a five-minute timestamp window and a unique PostgreSQL-backed nonce. Its signed response includes all active top-level sites automatically and inactive root entries needed for revocation. The caller verifies the pinned response signature over the **full catalog contents**, instance IDs, nonce, timestamp and schema version before storing snapshots. Older revisions are ignored. An omitted previously known site is locally suspended. `GET /api/platform/federation/peers/{instanceId}/catalog` lets Platform Manager inspect stored snapshots. Deactivating a peer suspends its local remote-site snapshots. Manual refresh remains available and is bounded to 2,000 entries and 1 MB; a paginated protocol is needed before larger deployments. Catalog entries appear in recipient search only while routing and the peer are active. Revoking or deactivating a peer stops future probes and catalog sync. No private key or full message payload should be logged.

Once both installations have approved and tested each other and enabled routing, all active top-level sites in their signed catalogs can exchange work in both directions. There is no site-pair or directional grant layer. Queueing, delivery and receipt each recheck routing, Enterprise entitlement, active peer identity, local top-level status and the active remote catalog snapshot.

Platform Manager navigation always includes a **Federering** page and always shows the complete setup surface. Without Enterprise, one prominent notice at the top says **Krever Enterpriselisens** and all federation mutations are disabled. Federation is included for valid Enterprise licenses issued before the `instance-federation` entitlement existed, so an existing license does not require reissue. The page shows the local identity and key state, peer discovery and proof, automatic top-level site visibility, catalog sync, routing readiness, activation/deactivation and the 100 newest outbound delivery records. Contextual help explains the complete bilateral procedure, and the user manual provides the detailed operating instructions. Activation is blocked unless HTTPS/proxy configuration, Enterprise entitlement, a usable signing key and a proven peer are present. The operator must also confirm the independent fingerprint check. Enabling and disabling are immediate, persisted and platform-audited. Disabling removes remote recipient selection, stops the outbox worker and makes the four work-message routes return 404, without deleting configuration or history. After license loss mutations remain denied server-side; persisted configuration and history stay visible.

The federation tables, including singleton `federation_routing_settings`, migrate in the normal shared database/schema. Existing installations receive routing disabled and no peer configuration; no local sites or tasks are modified. Database backup/restore must preserve this state with `instance_identity` and the Data Protection key ring. Work links relate one locally owned work item to its origin `(instanceId, siteId, resourceId)`, remote peer/site and eventual remote counterpart ID.

The outbound table reserves stable message IDs, schema/message type, source/destination and origin addresses, correlation/causation IDs, bounded payload, retry schedule and delivery state. When routing is enabled, ordinary primary, side and approved-plan request paths can select a locally authorized remote catalog entry and atomically commit the local request, outbound message and work link. The always-registered worker remains idle while routing is disabled; when enabled it claims due messages with an atomic database update and bounded lease, rechecks routing and site authorization, sends a freshly signed envelope over certificate-validated HTTPS and verifies the receiver's signed acknowledgement. A crash or lost acknowledgement can cause a retry with a fresh nonce; the receiver's durable message ID deduplicates it. Progress, approved official answers and cancellation use the same signed outbox/receipt path. Synthetic direct producers remain `FederationTest`-only.

Recipient search merges eligible local sites with remote entries only while routing is enabled and the exact active peer, catalog snapshot and Enterprise entitlement qualify. The UI carries the full `(instanceId, siteId)` into primary, side and planned request commands, which use the outbox adapter rather than a local `sites` lookup. Existing task, planning, execution, status and report semantics are reused rather than creating a parallel workflow. The maintained production-mode pair proves default-off isolation, GUI/API activation, ordinary recipient selection and signed delivery while all synthetic routes remain absent. Independent security review remains a release-governance gate; technical availability is not a statement that a particular organization has approved deployment risk.

## Message and correlation contract

A versioned, authenticated Fylkren-to-Fylkren envelope contains a globally unique message ID, schema version, message type, UTC timestamp, source and destination instance/site addresses, stable origin object address, counterpart address when known, correlation/causation IDs and a bounded payload. Before delivery, sender and receiver perform separately domain-signed, nonce-bound capability negotiation. `assignment.created`, `assignment.progress`, `assignment.answered` and `assignment.cancelled` have explicit v1 contracts and signed acknowledgements. Their production routes are mapped but return 404 while routing is disabled. The recipient creates its own local ID and durable origin mapping; return messages bind correlation/causation to the original assignment.

The isolated pair test covers an **origin** site moved under two successive parents after assignment delivery and, separately, a **receiving** site moved under a parent while it holds two in-flight assignments. The existing work links carried a signed official response on one assignment and a signed cancellation on the other, without allowing new work to the now-child site. Both report archives remained accessible for the answered assignment; the cancelled receiver task remained for local acknowledgement. Another test moves **both** sites below parents after assignment delivery, syncs inactive snapshots in both directions and still returns and archives the signed official answer. The outage-and-move test queues an answer while the origin is unavailable, moves the receiver before retry, and still delivers the same answer after recovery. Moving either site removes it from active top-level discovery and blocks new work until it is top-level again and the catalog is refreshed. Separate lock-coordinated races prove that answer and cancellation cannot both win and that a receiver-site move prevents a send whose authorization check occurred before the policy change but whose outbox commit occurred afterward. These remain isolated release evidence and must be repeated with the release candidate.

The v1 `FederationWorkEnvelope` cryptographically binds addresses, message/correlation IDs, timestamp, nonce, message type and SHA-256 hash of the exact UTF-8 payload bytes. The wire payload is capped at 256 kB. Signatures are domain-separated from probe and catalog signatures; protocol tests reject changes to destination, origin, counterpart, correlation, nonce or payload. The work receiver reevaluates the global routing switch plus active peer, local site hierarchy and peer catalog for every request.

Before creating a remote work item, the domain must represent external provenance correctly. The original `WorkItem.CreatedByPersonId` was a required FK to a local `Person`; using a random local leader or creating the remote human as a local user would misattribute the action and conflict with site-owned personnel management. The FK is now nullable for externally originated work, while locally created work continues to set it. An external item must carry a sender-site snapshot, and work/report projections use that snapshot when no local creator exists. The receive adapter must preserve separate remote sender-person and sender-site snapshots and the stable origin address in its work link. This model change does **not** create remote work by itself.

Technical audit now has separate actor representations: a local person ID, or a federated peer instance/site address and sender-site name snapshot. A database constraint permits exactly one representation. Site audit can display and search the sender-site snapshot, while a remote actor cannot be misreported as a local Platform Manager. Portable exports preserve the same audit provenance. In the isolated test receiver, a signed and currently authorized message creates the local task, idempotency receipt, origin work link and remote-provenance audit event in one database transaction.

The `federation_inbound_receipts` table holds the durable `(peerInstanceId, messageId)` idempotency key, origin address, payload SHA-256 and local counterpart ID. It is separate from nonce replay protection: retrying the **same** message with a fresh signed timestamp/nonce returns the original counterpart, whereas reusing the message ID with different content fails. It remains unused while routing is disabled.

The draft `assignment.created` payload contract is intentionally narrow: request/assignment kind, title, instruction, priority, deadline, request basis and source/sender **name snapshots**. It rejects extra fields, malformed priorities, overly long text and claims that an initial assignment originated from a different instance/site or already has a counterpart. The authenticated remote site name is resolved from the pinned peer's catalog rather than trusted as a payload string. No local person ID, unit ID, lookup ID, plan, subordinate report or internal history is part of this contract. The exact receiver API is not registered until delivery and official return flow can be exercised together.

Use a transactional outbound record and idempotent inbound processing with acknowledgements, bounded retries, observable delivery state, replay protection and poison-message handling. A transient peer failure must not roll back unrelated local work, but the UI must distinguish **pending delivery** from **received**. A replayed message must not create a duplicate assignment or report. Payload versions and capability negotiation must support rolling upgrades between compatible Fylkren versions. Ordering cannot rely solely on wall clocks.

The receiving site owns its internal planning, execution, personnel and subordinate reports. Ordinary status changes map to an `assignment.progress` envelope containing only a fixed external phase (`under_review`, `assigned`, `in_progress`) and monotonically increasing sequence number. No subordinate unit, person, plan or execution details are accepted in this payload. The origin accepts progress only for a previously acknowledged outgoing work link from the matching active, signed peer and exact site pair. Older deliveries are acknowledged without reverting the latest phase; the official answer takes precedence over any late progress. The ordinary request projection presents this coarse state without exposing receiver internals.

In the same isolated environment, an `assignment.answered` envelope returns only the receiver top-level site's official approved report (up to 20,000 characters, matching the existing report archive), its existing structured classification abbreviation when present, and approval timestamp. The origin accepts it only against its previously acknowledged outgoing work link and stores it as an immutable answer with its classification, a snapshot of the receiver's top-level site name and a remote-actor audit event; the origin's task is not auto-completed on receipt. The receiver's ordinary approved completion queues the answer and its completed work item belongs to its own site-level report archive. The origin site's ordinary leader close action accepts the answer, creates a local formal approval and completes the origin work item, making the same official answer and classification visible in the origin's report archive under the receiver's site-name snapshot. Existing classification markings in task text likewise remain inside the signed bounded task content; federation does not synchronize classification-definition IDs, names or policy configuration and performs no mapping. Later remote-site renames cannot rewrite that historical header. A return for an already accepted task follows its existing signed work link, although the peer must remain active and cryptographically authenticated. Do not tunnel internal audit events, raw database rows or private case files across the link. Document-reference handling remains outside this message contract.

The isolated `assignment.cancelled` path likewise addresses an already acknowledged work link. The sender's ordinary cancellation action queues a reason and retains its task until a signed receipt arrives. The receiver atomically changes its task to `request_cancelled` only if the task has not already been closed or formally answered. It does not delete the task or automatically complete downstream work; the receiving leader uses the ordinary acknowledgement/close action. A successful signed receipt then marks the sender task cancelled. Replayed delivery returns the same receipt without a second task or receipt record. The operator can inspect and retry permanent transport failure without seeing cancellation/report content. The dedicated browser-state acceptance and notification delivery-status presentation passed in the production-like pair; SMTP transport remains covered by the separate synthetic sink test rather than this pair run. The two sides' task/report history must remain readable after cancellation.

## Trust, entitlement and offline operation

Peers must be mutually approved by Platform Managers and authenticated at the server-to-server API boundary, with certificate or key rotation and revocation. The protocol must work over a private LAN or routed air-gapped network using a customer-controlled trust anchor; it may not depend on a public CA, cloud broker, vendor license call, public DNS or Internet time service. Protect integrity and confidentiality in transit, authenticate both peer identity and destination-site authorization, and reject unexpected instances, sites, message types, versions and replayed messages.

The Enterprise entitlement belongs at the federation capability boundary, not in the site or work-item domain model. Disabling routing or losing entitlement must not hide or erase historical received work, reports, correlations or audit records.

Audit peer trust changes, catalog changes, sends, receives, rejects, retries and correlation changes on the appropriate local side. Transport logs must omit secrets and private payloads. Each side remains responsible for its own data retention, backup, access decisions and incident response. By default, delivered outbound history and inbound receipts for terminal work, plus federation audit events, are retained for 2,555 days. Operators may configure 365–3,650 days. Daily cleanup is bounded to 10,000 rows per table and never deletes pending, retrying or failed messages, or receipts/outbox rows whose local work remains active.

## Required implementation gates

The persisted work-link model, versioned work-message schemas, signed capability negotiation, inbound/outbound transport, receiver authorization, ordinary return path, operator controls and a dedicated [federation threat model](../security/FEDERATION_THREAT_MODEL.md) are implemented in the production application and verified in isolated environments. The two-database test exercises mutual trust and revocation, tenant isolation, incompatible capability rejection, duplicate/reordered delivery, peer outage/recovery, sequential site moves, answer/cancellation and move/revocation races, cancellation, official reporting, operator retry, controlled lost-key replacement and real old/new-binary downgrade/upgrade delivery. The mixed-version fixture exports historical commit `152d0f2`, builds it as a distinct image, replaces one node while preserving its database and key volume, delivers both ways, upgrades it back to the current image and delivers both ways again. Separate modes prove retention and indexed reads under representative history, plus database-only restore failure and matched database/key-ring recovery without changing the peer pin. The supported path is TLS proxy → built web/Nginx gateway → API, with two forwarded-header hops configured explicitly. Production enablement still requires the threat model's remaining gates, including release-candidate repetitions, production backup-custody rehearsal and independent security review. Until those gates pass, the implementation must not be represented as independently approved federation.
