# Input validation rules

This document defines Fylkren's application-level input validation rules. It is the design reference for ASVS 2.1.1–2.1.3; requirement status and executed evidence remain in the single [ASVS matrix](ASVS_5.0.0_L2_MATRIX.md).

## Validation boundary and order

The API is the trusted validation boundary. Browser controls improve usability but never establish validity or authorization. ASP.NET decodes route, query and JSON input once into fixed request types. Endpoint or domain validation then applies these checks in order:

1. Reject malformed transport syntax, unsupported media, missing required values and values the fixed request contract cannot represent.
2. Normalize only where the domain defines normalization, normally `Trim`, case normalization for identifiers, or an explicitly expected base64/base32 decoder. Do not repeatedly URL-, HTML- or JSON-decode values.
3. Enforce positive structure, allowlists, lengths, counts, numeric ranges and date ranges before arithmetic, persistence or external use.
4. Resolve referenced records and enforce active state, Site ownership, hierarchy and cross-field consistency at the service layer.
5. Apply authorization independently of validity. A valid identifier never grants access.
6. For state changes, recheck expected versions and relationship constraints inside the database transaction before committing activity/audit records.

Validation failures use field-specific HTTP 400 responses where disclosure is safe. Stale versions and capacity conflicts use 409. Missing authority uses 403 without treating a valid object reference as authorization. Authentication failures remain generic. Unhandled exceptions and stack traces are not validation responses.

## Combined and contextual rules

Individual fields can be valid while the command is invalid. Service-layer validation must therefore cover at least these relationships:

- a Site or organizational move must reference an active permitted parent and must not create a cycle;
- a task dependency must stay within the allowed ownership scope and must not create a dependency cycle;
- exactly one allowed recipient form is selected for a side request, and internal/federated recipient rules match the source placement;
- decision makers, risk owners, learning owners and other people references are active and visible at the required Site/level;
- risk probability and impact pairs are complete and in range before a score is derived; residual values represent the post-measure state;
- lifecycle transitions use the current expected version, satisfy blockers and preservation holds, and never enable irreversible disposition;
- report, audit, activity and archive filters remain inside the caller's authorized Site/level scope regardless of filter validity;
- imported rows belong to the package Site, referenced owners exist in the package or accepted historical scope, and declared content matches its integrity descriptor;
- federated progress, answers, cancellation and grants match the existing local link, peer, origin and direction.

## Business limits and scope

Limits have an explicit scope. Per-command limits prevent one request from creating an unexpectedly large object. Per-account/client limits slow repeated security-sensitive work. Site/installation limits constrain licensed or operational capacity. A limit in one scope must not be described as protection in another scope.

| Scope | Current expectation and enforcement | Residual or follow-up |
| --- | --- | --- |
| One command | Apply the field, collection and package limits above before persistence. Examples include 20 decision makers/references, 30 workflow steps, 50 learning points, 100 allocations/timeline events, 200 bulk users, 250 portable entries and 16 MiB declared portable size. Rejected commands are atomic. | Every new command must declare its own text/count/byte and relationship limits. |
| One local account | Twenty failed password checks lock the account for 15 minutes. The counter saturates rather than wrapping. Session/version, reset, MFA and passkey operations retain their one-time or monotonic rules. Authenticated browser identities receive at most 600 reads and 120 mutating requests per fixed minute across the API. | Fylkren does not impose a lifetime per-account object quota. Rate control bounds creation speed; Site/database storage sizing and monitoring remain deployment responsibilities. |
| One authentication client address | Browser authentication permits eight requests per fixed one-minute window and returns 429 with `Retry-After`. Forwarded client identity is trusted only through the configured gateway boundary. | Distributed attempts across addresses and account/client combined throttling remain anti-automation assessment scope. |
| One machine API identity | Administration API endpoints permit 120 reads and 30 writes per fixed one-minute window after authentication. Credential verification has a separate bounded/concurrent gate documented in the [API conventions](../api/API.md#rate-limiting-and-credential-protection). | These limits protect each machine partition; deployment-wide traffic capacity is measured separately. |
| One federation client partition | Probe and capability endpoints each permit 20 requests per fixed one-minute window. Message bodies, discovery documents, remote responses and retry attempts also have explicit size/count ceilings. | A deployment proxy may add stricter global/network controls; application partitions do not replace them. |
| One Community installation | At most three active Sites, including child Sites. The same shared policy applies to UI and machine creation. A fourth active Site returns 409 without disabling existing Sites. Enterprise entitlement removes this edition limit. | This is a licensing/business limit, not a tested hardware or database-capacity statement. |
| Costly operation per identity/client | Export and remote federation discovery/synchronization permit six calls per fixed minute. Provider/directory/SMTP connection tests and portable import validation have separate 30-per-minute partitions so maintained negative transport/parser checks remain usable. All rejections return 429 with `Retry-After`. | The common browser limit also applies. Machine and federation protocol limits remain independently stricter where documented. |
| One installation/data set | There is no product-wide lifetime quota for total users, tasks, comments, decisions, risks, reports, attachments, audit events or activity events. Database/storage sizing, monitoring and backup capacity are deployment responsibilities. Pagination, per-request bounds and identity/client request-rate controls still apply. | Absence of a product storage quota must not be presented as verified unlimited scale. Supported capacity and deployment alarms remain release sizing work. |

Rate and edition values are centralized in [ServiceRegistration.cs](../../apps/api/ServiceRegistration.cs) and [SiteCapacityPolicy.cs](../../apps/api/Licensing/SiteCapacityPolicy.cs). Operational capacity claims require the separate [performance verification](../operations/PERFORMANCE_VERIFICATION.md); they are not inferred from validation tests.

## Change requirements

Every new or changed input must document its expected structure, normalization, allowlist/range, maximum size/count, relationship rules, authorization boundary and failure response. Tests must include a valid case, invalid type/shape where applicable, boundary values and a related-data or authorization case. Shared rules belong in a shared production validator; UI validation must mirror them for usability without becoming the security control. The ASVS matrix links executed evidence and remains the only requirement-status record.
