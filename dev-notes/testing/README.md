Automated frontend tests currently live beside their source files as `*.test.ts` and run with `pnpm test`. API build and repository checks are part of the reproducible gate in [technical cleanup verification](../operations/CLEANUP_VERIFICATION.md). A full automated PostgreSQL/API integration suite has not yet been established; a successful frontend test run must not be reported as an end-to-end result.

`pnpm test:e2e:local` (alias `pnpm test:e2e:editions`) starts the **disposable** `fylkren-edition-e2e` Compose project on `127.0.0.1:18081`, runs API-level synthetic regression chains, and removes that specific project's volumes afterward. It bootstraps separate platform/site/leader identities; exercises Community/Enterprise entitlements with pre-signed synthetic fixtures; runs a local task through planning, explicit release, execution and final-report archive; distributes another task through a section to a team, with a separate approved report at all three levels; and returns a parent-to-child-site official report. It also moves a child site with active work to a new parent and then makes it independent, checking that reports follow the original assignment relationship and sender snapshots do not change. Invalid placement and authorization boundaries are tested. It refuses to run against an initialized database and checks a reserved disposable instance ID. The harness may pause for authentication rate limits. It does not test browser layout, PDF output or the full acceptance matrix. Never point the underlying test script at an ordinary deployment. Generated passwords remain in memory and are not printed.

`pnpm test:e2e:license-expiry` starts the separate disposable `fylkren-license-expiry-e2e` project on `127.0.0.1:18087`. It generates an ephemeral P-256 test issuer in memory, installs a license that expires against the real system clock, and proves downgrade without API restart. The test covers loss of machine API, webhook, external-identity and federation mutations; closure of inbound federation; preservation of sites and protected identity configuration; Community site capacity after downgrade; webhook-worker pause; and renewal plus worker/API resumption. The private test key is never written to disk or Git. The project and volumes are removed afterward. Never point this harness at a non-disposable installation.

`pnpm test:e2e:identity-directory` starts the disposable `fylkren-identity-directory-lab` project with a pinned OpenLDAP service and an ephemeral laboratory CA. It configures LDAP through the protected Platform Manager API, verifies secret redaction and LDAPS trust, links a separate local anchor through `entryUUID`, performs a real password bind, and proves authoritative suspension, existing-session rejection, restoration, profile synchronization and outage fail-safe behavior. The [2026-09-29 OpenLDAP run](runs/2026-09-29-live-openldap-identity.md) records the clean result and exclusions.

`pnpm test:e2e:identity-ad` starts the disposable `fylkren-identity-ad-lab` project with a pinned Samba Active Directory domain controller. It verifies certificate-name validation over LDAPS, `sAMAccountName` lookup, binary `objectGUID` linking, a real password bind, `userAccountControl`-based suspension, session rejection, restoration and outage fail-safe behavior. The Samba container's elevated capability is confined to the test topology and is not a production dependency. The [2026-09-29 Active Directory run](runs/2026-09-29-live-active-directory-identity.md) records the clean result and exclusions.

`pnpm test:e2e:identity-sso` starts the disposable `fylkren-identity-sso-lab` project with pinned Keycloak, a TLS gateway and headless Chromium. It configures providers through the Platform Manager API, verifies OIDC secret redaction and trusted HTTPS metadata, completes a real authorization-code login, proves stable issuer/`sub` linking and the server-side browser-token boundary, then completes a signed SAML login with a persistent NameID. Negative controls reject mismatched issuer metadata, forged state, replayed OIDC callbacks, signature-tampered SAML assertions and replayed SAML responses without retaining a local session. The [2026-09-29 OIDC/SAML run](runs/2026-09-29-live-oidc-saml-identity.md) records the clean result, findings, corrections and remaining exclusions. All three identity commands create and destroy their own named projects and volumes; never direct them at an ordinary deployment.

`node tools/e2e/community-browser-smoke.mjs` adds a focused Chromium check when `FYLKREN_BROWSER_CDP_URL` points to an isolated DevTools endpoint and `FYLKREN_BROWSER_TARGET_URL` points to the disposable web service. It bootstraps through the rendered form, creates one site through the UI, checks Community license/federation presentation, desktop/mobile overflow and browser errors. The target must be empty and disposable; the script deliberately fails if first-run setup is unavailable. The [2026-09-27 browser run](runs/2026-09-27-community-browser-smoke.md) records the exact topology and exclusions.

Adding `--enterprise` continues from that Community baseline by selecting a pre-signed synthetic JSON license through the rendered file control, checking Enterprise federation and API controls, removing the license through the confirmation dialog, and verifying both the restored Community boundary and preservation of the existing site. Chromium must be able to read the upload fixture at `FYLKREN_BROWSER_LICENSE_PATH` (default `/test/license-upload-fixture.json`); mount `tools/e2e/license-upload-fixture.json` there read-only. The disposable instance ID and public issuer key must match `tools/e2e/license-fixture.json`. The [2026-09-27 Enterprise browser run](runs/2026-09-27-enterprise-browser-transition.md) records the exact result and exclusions.

Adding `--task-flow` instead creates an isolated site and two top-level leaders, signs into the rendered application as the report author, and exercises the E2E-01 registration, assessment, direct-execution and final-report path. It changes accounts after the report is saved so a separate leader approves and completes it, then verifies both identities in stored state and the rendered archive. It also persists an HTML/script event-handler payload through the ordinary task form and requires Chromium to display the literal text without creating active elements or executing the marker. Overview counters before and after completion, 12-month workload API/UI presentation at active totals `1` and `0`, the rendered site-audit chain, and pending notification deliveries while SMTP is disabled are checked as well. Administrative fixture creation and delivery inspection use authenticated APIs; every operational transition uses rendered browser controls. The [2026-09-27 E2E-01 browser subset](runs/2026-09-27-e2e-01-browser-direct-execution.md) records the original path, its [observability follow-up](runs/2026-09-27-e2e-01-browser-observability.md) records the added controls, the [workload/classification follow-up](runs/2026-09-27-e2e-01-workload-classification.md) records the chart and explicit example classifications, and the [separate-approver follow-up](runs/2026-09-27-e2e-01-separate-report-approver.md) records actor separation. `--enterprise` and `--task-flow` are intentionally mutually exclusive so each run has an unambiguous evidence scope.

Adding `--smtp` to `--task-flow` enables the platform transport against the isolated `smtp-sink` service from `tools/e2e/browser-smtp.compose.yaml`. Before valid configuration, the harness requires a CRLF/Bcc display-name payload to be rejected. The sink accepts only `example.invalid`, rejects the first message with SMTP `451`, and exposes decoded message metadata only through a host-loopback inspection port. The browser harness requires the application's delivery view to expose the pending retry, waits for the normal exponential backoff, requires final `sent` state and an empty projection backlog, then checks that the originally rejected recipient received a message containing the task title and link. The [2026-09-27 SMTP retry/mailbox follow-up](runs/2026-09-27-e2e-01-smtp-retry-mailbox.md) records the original clean run. This is closed-laboratory evidence; it does not cover STARTTLS, authentication, an external relay, DNS or delivery to a provider-operated mailbox.

Adding `--keyboard` to `--task-flow` exercises the task-registration dialog with DevTools keyboard input rather than synthetic DOM clicks. It requires `Enter` activation, a named modal in Chromium's accessibility tree, initial focus inside the dialog, forward and reverse focus containment, a visible keyboard-focus indicator, `Escape` dismissal and focus restoration to the opener before reopening the dialog and completing the ordinary E2E-01 chain. The [2026-09-27 keyboard-dialog follow-up](runs/2026-09-27-e2e-01-keyboard-dialog.md) records the product correction and clean run. This focused control does not claim a full screen-reader audit, complete keyboard coverage of every page or another browser engine.

Adding `--classified-pdf` to `--task-flow` retains the synthetic report as `output/pdf/e2e-01-classified-report.pdf`. The synthetic fixture explicitly creates the example choices `PUBLIC`, `INTERNAL`, `CONFIDENTIAL`, `SENSITIVE`, `SECRET`; they are not product defaults. The flow asserts their order, selects `CONFIDENTIAL`, verifies the stored `CONF` abbreviation and full archive marking, and supplies a deterministic long report to the application's PDF-export document. A separate Chromium target captures the A4 output before an automated verifier requires at least three substantive pages, both classification markings on every page, both actor identities, the first and final content markers, and a passive unencrypted document. The [2026-09-27 classified PDF follow-up](runs/2026-09-27-e2e-01-classified-report-pdf.md) records the original single-page control, while the [multi-page follow-up](runs/2026-09-27-e2e-01-multi-page-classified-report.md) records the current four-page result and the print-layout correction it drove. Without this flag, the classified browser assertions still run but no artifact is written.

The same run also sends work through three sites (parent → child → grandchild). It verifies one recipient item at the grandchild, a separate approved report and archive at each site, and that the grandchild report is visible to its direct parent but does not bypass that site or become the top parent's official response. The active grandchild task must count once in both the child site's direct-child workload summary and the top site's recursive child-site summary. Multi-child fan-out and browser-level workload presentation remain outside this automated chain.

The cross-site request scenario uses two independent top-level sites. It verifies that sending a request preserves the source task, creates one sender tracking item and one receiver-owned item, keeps receiver details and execution inaccessible to the sender, returns only the approved official response, and stores that response in both sites' report archives. A second request is withdrawn with a reason; the receiver sees the cancellation and acknowledges it, leaving terminal states on both sides. Browser presentation, production notification delivery, optional planning/delegation within the receiver, report PDF headers and active dashboard counters still need separate verification.

This request scenario passed twice on 2026-09-23 against fresh isolated PostgreSQL/Compose instances, including the final check that the source task remains readable after request creation. A subsequent isolated run on the same date enabled the relevant site notification categories and confirmed pending outbox messages for receipt at the receiver, official response at the sender and withdrawal at the receiver. Another fresh run enabled SMTP against a local synthetic sink: those event deliveries reached `sent`, and the sink accepted the messages. This does **not** verify a real mailbox, STARTTLS, authentication or retry. This is an API-level subset of [E2E-08](END_TO_END_TEST_MATRIX.md#e2e-08--direct-request-between-top-level-sites), not a completed browser acceptance run. The behavior and operator steps are described in [Tasks and operational flow](../../docs/administration/WORKFLOW_AND_TASKS.md#cross-site-requests), the [user manual](../../docs/administration/USER_MANUAL.md#cross-site-request) and [Email notifications](../../docs/operations/NOTIFICATIONS.md).

Additional clean API runs on 2026-09-23 exercised cross-site requests created by leaders in Section 1, Staff and Team Alpha. The independent receiver saw the top-level site as official sender, completed its own report, and returned the official response to each exact originating level's report archive. The final run also exercised internal requests from Section 1 to Team Alpha and to sibling Section 2; each receiver completed its own report and the response was archived at Section 1. Same-site overview legitimately contains both the section's request-tracking item and the received task; assertions identify each by relationship and ID, not title alone. This covers the routing and report-return portions of [E2E-09](END_TO_END_TEST_MATRIX.md#e2e-09--requests-from-subordinate-levels) at API level. Browser presentation, per-level counters, notification recipient rules for every origin and the complete clean manual acceptance run remain open.

The isolated SMTP handoff evidence above used `tools/e2e/smtp-sink.mjs`, which rejects recipients outside `example.invalid` and exposes metadata only on loopback. The edition runner creates and removes its Compose project automatically; its network does not exist before the run. The browser variant uses the dedicated Compose override described above and must likewise run only with freshly created disposable volumes. Do not direct the API harness, browser harness or sink at an ordinary deployment.

Overview-model regression tests on 2026-09-23 additionally verified that a side request does not replace its active source task; sent requests remain a separate live count and remain in annual statistics after closure; an official response enters the sender's action list until closed; the source can then require its own next action; a received request counts once; and a withdrawn request leaves the receiver's active/action lists after acknowledgement. Tests also cover a source with both an internal delegation and a side request. These are frontend-model tests, not a visual browser or production-deployment verification.
